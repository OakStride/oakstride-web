Four tests that passed without testing anything

A test that checks nothing looks exactly like a test that passed. In five days we found four of them in our own build. I committed the last one while writing this very article.

We build a lot of automation: tests that run before anything is published, checks meant to speak up when a database and its source code drift apart, alarms meant to sound when something is wrong. They all exist for the same reason — so that a human does not have to hold everything in their head.

And they all share the same weakness. A green result only means the test did not find anything. It says nothing about whether the test looked.

1. The dry run that never touched the database

We have a tool that applies database changes, and it has a dry-run mode. I had just written a new change file and planned to dry-run it first, to see that it was syntactically sound before running it for real. Reasonable enough.

The dry run prints would run: filename and turns green. It never starts the database client. It does not read a single line of the contents. It would have said exactly the same thing if the file had contained pure nonsense.

The mode is not broken — it does what it was built for, namely to show which files would run and in what order. The mistake was mine: I was about to let it answer a question it had never asked.

2. The check that searched for itself

The day before, I had written another database change with what I described as a built-in safeguard: a post-check that would abort if the change had not taken effect. I highlighted it in the description. It felt responsible.

The check looked for a text string. That string sat in the same file's own body. It could therefore never be absent, and the check could structurally never fire. I had written zero lines of protection and described them as a safety net.

3. The alarm nobody has seen fire

The same tool has a mechanism that is supposed to lift a warning out of the database client's output and surface it as a visible annotation on the run. I referred to it in a comment and justified a design choice with the claim that the warning would be seen.

A review went through all eight runs the tool has ever had. Not one of them contains a single such annotation. The code looks right when you read it. Nobody has seen it fire. The difference between read and seen working is the whole point of this article.

4. The test that was true by construction

This is the most embarrassing one, and it happened today — while I was gathering material for this very article.

I had written a change that was supposed to be inert in production: it merely records something that already holds. To prove it, I built in a check that measures the function before and after and requires it to be byte-for-byte identical. Then I ran the test.

But I left out the one statement that changes anything — precisely because I had concluded it was inert anyway. Which is the very thing the check existed to prove. Without that statement, nothing touched the function between the two measurements, so the equality was true by construction. The result the check ran and held could not have come out any other way.

A reviewer caught it. The fix was simple: run the whole file, including that statement, inside a transaction that is rolled back afterwards. Everything gets exercised, and nothing remains. It took five minutes. The hard part was never the fix — it was noticing that the test was not testing.

What the four have in common

None of them is carelessness in the ordinary sense. All four were written by someone being careful, and three of them were read by several people without anyone reacting. What they share is something else:

  • The output looks the same either way. A test that tests nothing prints the same green line as one that passed.
  • The fault lies in what the test does not do, and that shows up in no field at all.
  • It cannot be caught by paying closer attention — all four were read by someone paying attention.

What actually helped

One single habit, and it is an uncomfortable one: make the test fail on purpose. If you cannot make it fail, you do not know whether it can genuinely pass.

When we extended our sitemap test from is this well-formed XML to does every address lead to a page that exists, we tested it both ways: fourteen real addresses passed, and one deliberately misspelled one was caught. It is the second half that makes the first half worth anything.

We write this openly because it is tempting to assume this kind of fault only strikes sloppy builds. It does not. It strikes builds where somebody cared enough to write tests — and then trusted them.
